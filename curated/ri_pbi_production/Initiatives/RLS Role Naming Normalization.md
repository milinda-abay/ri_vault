# RLS Role Naming Normalization

Cross-repo initiative to make RLS **role names** consistent with each repo's own master-list identity — started 2026-08-06, still open. Narrower sibling of [[RLS Alignment Audit]], which covers filter-column unification and governance-tier gaps; this one is naming-only.

## Purpose

The five RLS-enabled repos other than [[Survey RLS|Survey]] — [[Awards RLS|Awards]], [[Finance RLS|Finance]], [[iLab Utilisation RLS|iLab Utilisation]], [[Publication RLS|Publication]], [[Risk RLS|Risk]] — each evolved role names independently for the same underlying RI platforms/capabilities. [[RLS Alignment Audit]] had already flagged the resulting drift (e.g. `FENG-DCE` vs `DCE`, `FLOW` vs `FLOW-ARA/CLAYTON/MHTP`, `MBI` vs `MBI-ARA/MBI-CLA`, `HMST` vs `MMIC-HMST`) but never checked role literals against live data.

The design settled a **hard constraint: naming only**. No `tablePermission` expression, filter column, operator, or filter value may change; no role may be added, removed, split, or merged — every existing role file maps 1:1 to a renamed role. `TESTING` roles and ilab's unrestricted `DVCRE-ADMIN`/`PVCRI-ADMIN` are excluded outright. [[Asset]] has no roles (nothing to rename) and [[Survey]] was ruled out of scope on 2026-08-06 because its `DIM_FACILITY` table had no `CAPABILITY_CODE`/`NODE_ID`, only `SURVEY_CAPABILITY_ID`.

> [!warning] Premise changed — needs re-evaluation before this initiative next moves
> As of the `ri_pbi_production` export on 2026-09-15, `DIM_FACILITY` widened to 25 columns and **does now carry `CAPABILITY_CODE` and `NODE_ID`** — see [[Survey Data Model]]. Whether this reopens Survey's exclusion depends on questions this initiative hasn't answered: does `DIM_FACILITY` still hold only survey-relevant rows (unconfirmed post-widening), and has any role file actually started filtering the new columns (also unconfirmed — role files aren't in this export). Don't reopen Survey's scope on this note's say-so alone; re-derive from live `roles/*.tmdl` and a fresh Databricks pull first.

**Canonical naming algorithm** (from the design spec): for every role, pull its filter literal(s) unchanged, then rename the role to match that literal — verified against a live pull of each repo's own master-list table, not inferred from today's file names:
- Single-value filter → canonical name = the literal, once confirmed present in live master-list data.
- Governance filter (`[CAPABILITY_GOVERNANCE]`) → literal + `-ADMIN` suffix.
- Unrestricted role (no `tablePermission`) → fixed exception, name untouched.
- Multi-value filter → no change if all values share the current name as a common stem; otherwise flagged for human review, not guessed.
- `TESTING` → excluded entirely.

Because role *granularity* is fixed by the hard constraint, this does **not** merge naming across repos — e.g. publication's single `MMI` role and awards' three `MMI-ARA`/`MMI-CLA`/`MMI-MHTP` roles both end up correctly named for what they individually filter, not forced into agreement.

## Approach / tooling

A two-phase pipeline, built and run from the workspace root (`tools/rls-role-naming/`), following TDD-style verify-then-build steps per task:

**Phase A — data pipeline (workspace root, its own commits):**
1. `Get-MasterListValues.ps1` — pulls distinct `CAPABILITY_CODE`, `NODE_ID`, `ILAB_CAPABILITY_ID`, `CAPABILITY_GOVERNANCE` values straight from Databricks (catalog `pen_research_infrastructure_insights_prd`, schema `ri_lakehouse`, table `ri_master_list`) via the SQL Statement Execution API — confirmed the *same physical table* backs all five repos' `dim_ri_master_list`/`dim_facility_master_list` (finance's is just a column-projected subset), so one query covers everyone.
2. `Get-RoleDefinitions.ps1` — parses all 224 `roles/*.tmdl` files across the 5 repos into `docs/rls-role-naming/data/all-roles.csv`.
3. `Compute-RoleMapping.ps1` — joins the two, applies the naming algorithm, and produces `docs/rls-role-naming/mapping/role-mapping.csv` (one row per role, with a `Status`) plus `needs-human-decision.csv` for anything unresolved.
4. `New-HandoverDocs.ps1` — renders human-readable per-repo mapping tables and old→new handover lists from the CSVs.

Each step has a matching `Test-*.ps1` that fails before the step runs and passes after, and each task is a separate workspace-root commit.

**Phase B — apply renames (per repo, committed inside that repo):**
- `Rename-Roles.ps1` — generic script, reused unmodified across repos: for every row with `Status = renamed` in that repo, `git mv`s the `.tmdl` file and rewrites its `role <Name>` line. Verified afterward that each changed file's diff touches *only* that one line.
- Discovered live during the [[iLab Utilisation]] run: renaming a role file also leaves a dangling `ref role <OldName>` line in `model.tmdl` — fixed by hand in that repo (`Fix dangling model.tmdl role reference after HMST -> MMIC-HMST rename`) and then folded back into the generic script itself (`Rename-Roles.ps1: also update model.tmdl's ref role line on rename`), so later repos don't hit the same gap. A separate hardening pass (`Fix: Add per-row error handling and resumability to RLS role-rename script`) made the script resumable after a partial failure.
- Intended commit message for each repo's rename: *"Rename RLS roles to canonical master-list-derived names"*, pointing back to that repo's handover doc at the workspace root.

Overall `role-mapping.csv` status breakdown across all 224 roles: 206 `no-change`, 1 `renamed`, 3 `no-change-testing-excluded`, 2 `no-change-unrestricted-exception`, 2 `no-change-multivalue-stem-verified`, 9 `flagged-not-found-in-master-list`, 1 `flagged-multivalue-review`.

In short: the drift the [[RLS Alignment Audit]] worried about was mostly **already correctly named** once checked against live data — the pipeline found very little to actually rename. What it *did* surface, via the 10 flagged rows, was a smaller set of genuinely broken or ambiguous roles, most of which have since been patched by hand outside the tracked plan (see Open items).

## Open items

From `docs/rls-role-naming/mapping/needs-human-decision.md`, which splits the original 10 flagged roles into two categories — and cross-checked against current TMDL state (2026-08-20) to note what's since moved:

**(a) Genuinely ambiguous names, no evidence of a functional problem:**
- [[Awards RLS|Awards]] `NANO` — **resolved** manually to `MCN` (2026-08-10).
- [[Publication RLS|Publication]] `NANO` — **resolved** manually, role deleted in favour of existing `MCN` (2026-08-10).
- [[iLab Utilisation RLS|iLab Utilisation]] `DDP` — **still open**, untouched by any commit so far.
- [[iLab Utilisation RLS|iLab Utilisation]] `HELIX` — **resolved** manually; filter values corrected to `MERC-HELIX` (2026-08-10), name kept as `HELIX`.
- [[iLab Utilisation RLS|iLab Utilisation]] `DMAE` multi-value ambiguity (`FENG-DMAE|FENG-FETS`, which name should win) — **resolved** manually, renamed to `ENG-DMAE` (2026-08-10).

**(b) Filter literal absent from live master-list data — flagged as a potential RLS access defect, not just naming** (roles possibly granting members **no visible data at all**):
- [[iLab Utilisation RLS|iLab Utilisation]] `DCE`, `DCHME`, `DECSE`, `DMSE`, `FETS` (and the `FENG-DMAE` half of `DMAE`) — all filtered `CAPABILITY_CODE` values that live Databricks data showed never occur in that column. **All resolved** in the 2026-08-10 manual pass (`beb91c3`) — renamed to `ENG-*` and, notably, `DMSE` and `HELIX` also had their filter *column* switched from `CAPABILITY_CODE` to `NODE_ID` with corrected values, which fixes the underlying access defect, not just the label. This exceeds the initiative's original naming-only scope but was evidently judged necessary and done deliberately.

> [!warning] Correction — `ENG-DMSE`'s missing second filter was **not** fixed
> The 2026-08-10 pass (`beb91c3`) is easy to read as having repaired this role completely. It did not. What it corrected was the filter **column and value**: `[CAPABILITY_CODE] IN {"FENG-DMSE"}` → `[NODE_ID] IN {"ENG-DMSE"}`.
>
> The separate `dim_ilab_services[facility_id]` filter that ~46 sibling platform roles carry is **still absent**, verified against TMDL on 2026-09-01. `MGBP-BI` has the same gap. So [[RLS Alignment Audit]]'s low-severity finding on those two roles remains live: `dim_ilab_services` rows stay visible to them.
>
> Two different defects were reported together in the same sentence of the source material, and only one was fixed. See [[iLab Utilisation RLS]].
