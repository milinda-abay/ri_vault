# `ri_external_institutes` SCD2 Migration

`pen_research_infrastructure_insights_prd.standalone_bronze.ri_external_institutes` maps external (non-Monash) client organisations to their SAP client number (`SAP_CLIENT_NUMBER`), sourced from a manually curated Google Sheet — the join key between SAP customer master data (`lakehouse_psa_prd.sapfinance.kna1`/`knb1`) and Monash's own institution naming/classification for external institutes.

This note is the single source of truth for this table. It absorbed `docs/2026-08-29-ri-external-institutes-scd2.md` from the `ri_ilab` repo on **2026-09-08**; that file has been deleted.

> [!note] Reconciled against the `ri_ilab` export at `1ac3015` (2026-09-19)
> Checked against the export: the absorbed repo doc has no graphify nodes, consistent with its deletion, and the derived links in See also resolve. Everything else is live Databricks state from the dated checks in this note, which the export doesn't carry.

## Before/after

Before this migration, every rebuild did a full `overwrite` — a plain replace with no history. Any edit or deletion in the Google Sheet was silently and permanently lost on the next run; there was no way to answer "what did this institution's SAP client number used to be" or "when did this row change." This brought it in line with [[ri_master_list SCD2 Reference|ri_master_list]], which had the identical problem and was migrated to SCD2 first.

**Design note**: unlike `ri_master_list` (which splits into a full-history bronze table plus a separate active-only table Power BI actually reads), `ri_external_institutes` has no downstream consumers requiring that split, so it stays as **one table** carrying the SCD2 metadata columns directly. Anyone querying it for current state needs `WHERE _ROW_ACTIVE_FLAG = 'Y'`.

## Source of truth and rebuild pipeline

Google Sheet (`external_institues` tab, the sheet-tab typo baked into the original notebook name) → build notebook → the single SCD2 table, no separate history table or view.

- **Build notebook**: `ri_external_institutes_bronze` (renamed 2026-09-02 from `ri_external_institues`, matching the `<table>_bronze`/`<table>_bronze_validate` convention now used across `ri_standalone/` — see [[Databricks Conventions]]). Reads the sheet into a Spark DataFrame using a fixed 7-column schema (`institution_name, institution_type, sap_client_number, abn, country, state, postcode`), converts empty strings to `NULL`, uppercases column names, then runs the SCD2 merge (below) directly against the target table.
- **Schedule**: bundled as the `ri_external_institutes_bronze` task (renamed from `ri_external_institutes`) in job **"01_standalone_tables"** (job id `163544004016522`, renamed from "Daily run - ri_master_list"), alongside the `ri_master_list_bronze` → `ri_master_list_bronze_validate` chain (renamed 2026-09-03 from `ri_master_list` → `test_ri_master_list` — see [[ri_master_list SCD2 Reference]]) — it runs independently of those two. A validation task now runs on success of this task (see [Validation notebook](#validation-notebook) below). **Not** the same classic job cluster as the rest of the job: of the job's 8 tasks, only the three bronze **build** tasks (`ri_master_list_bronze`, `ri_external_institutes_bronze`, `remap_tables_bronze`) run on the classic `ri_master_list_cluster` (`Standard_D4ds_v5`, cluster policy `001F54073034F458`) — they need Google Sheets egress. The other 5 (all three `*_bronze_validate` tasks plus both silver tasks) are serverless.
- **Silver rebuild, added 2026-09-12**: the chain now continues past `ri_external_institutes_bronze_validate` into two more tasks in the same job, both `run_if: ALL_SUCCESS`: `ri_external_institutes_silver` (rebuilds `standalone_silver.ri_external_institutes`) then `ri_external_institutes_silver_validate`. Before this date the silver table sat in **no job at all** — it was hand-run, last manually rebuilt 2026-09-02 — and because silver carries bronze's `_START_TIMESTAMP` through unchanged (see [[Databricks Conventions]]), a silver table 10 days stale looks no different, in its own columns, from one rebuilt an hour ago; nothing in the row values would have shown it. That blind spot is why the new validate notebook checks silver against bronze directly rather than re-checking silver's own shape when run **standalone**. Inside the job, though, the two bronze-parity checks stop acting as staleness detectors — bronze was rebuilt minutes earlier in the same run, so they instead guard **transform correctness**; staleness in the job is surfaced a different way, by the job **failing** (a bronze or bronze-validate failure skips both silver tasks as `UPSTREAM_FAILED`) and by the job's failure email (added 2026-09-14, see below), not by these checks. Both new tasks are **serverless** — no cluster reference at all, which is what makes them serverless — while the three bronze build tasks stay on the classic `ri_master_list_cluster` because they need Google Sheets egress. The silver notebook writes via `df.write.mode("overwrite").saveAsTable(...)`, which Delta **logs** in its history as `CREATE OR REPLACE TABLE AS SELECT` — the write is atomic, so a failed unattended run leaves the previous table intact. That's materially different from the **`ilab_*_bronze`** notebooks (the legacy `ri_ilab` Python-pipeline bronze builds — not the `standalone_bronze` notebooks in this job), which do `DROP TABLE IF EXISTS` followed by `saveAsTable`: a failed write there leaves no table at all. The `standalone_bronze` build notebooks in *this* job instead close affected rows with a `MERGE` and then `append` the new versions, which also never drops the table. Validation runs **after** silver is published, so a `ri_external_institutes_silver_validate` FAIL means the bad table is already live, not caught pre-publish; recovery is `RESTORE TABLE pen_research_infrastructure_insights_prd.standalone_silver.ri_external_institutes TO VERSION AS OF <n-1>`.
- **Validate notebook hardened, 2026-09-14**: `ri_external_institutes_silver_validate` gained a new `silver_not_empty` FAIL check (an empty silver previously passed every other check vacuously, since every comparison was `0 == 0`), and `derived_country_columns_populated` changed from WARN-only to WARN for 1–5 unmatched rows / FAIL beyond that (a total failure of the shared `lakehouse_bim_prd.country.country` lookup would otherwise have shipped as a non-blocking WARN) — see [[Databricks Conventions]]. The notebook now runs **15** checks, not 14.
- **Retries added 2026-09-12, extended 2026-09-14**: `ri_external_institutes_bronze` carries `max_retries: 2` / `min_retry_interval_millis: 300000` since 2026-09-12 (as does `ri_master_list_bronze` — see [[ri_master_list SCD2 Reference]], which records the full egress-failure diagnosis table that motivated this; not restated here). Of the 11 scheduled (PERIODIC) runs between 2026-09-02 and 2026-09-12, **4 failed** — 2026-09-04, 09-08, 09-09, 09-11 — with `OSError: [Errno 101] Network is unreachable` or an `HttpError 503` inside `GoogleSheetReader`; the additional 2026-09-02 failures were hand-started **ONE_TIME** runs, not scheduled ones. `remap_tables_bronze` reads Google Sheets too — via a `GoogleSheetReader` for sheet `1vXB6v0wt3m3Lsl3JSSY4XvPtkXzFxlE-VMo6iYG_JGA`, not inline literals (the inline `REMAP_*` literals live in the `ri_ilab` Python repo, not this notebook — see [[Standalone Remap Tables Reference]]) — and failed the same way on 2026-09-04 (`OSError: [Errno 101] Network is unreachable`). It was left out of the 2026-09-12 change; on **2026-09-14** it got the same `max_retries: 2` / `min_retry_interval_millis: 300000` policy, so all three Sheets-reading tasks in this job now retry. The same job `jobs reset` also added job-level `email_notifications.on_failure: ["milinda.abayawardana@monash.edu"]` as of 2026-09-14 (`no_alert_for_skipped_runs` unchanged at `false`), so any task failure in the job now sends a failure email. One inert side effect, both times: applying the change via `databricks jobs reset` also materializes `retry_on_timeout: false` on each newly-retried task — harmless, since all three carry `timeout_seconds: 0` (unbounded), so no timeout can ever fire to retry on. Verified live via `verify_payload.py`: `VERIFIED: 8 tasks, no unintended changes`. **Mechanism confirmed 2026-09-15, real failure still untested**: every scheduled run since 2026-09-12 has gone straight to `SUCCESS` on attempt 0, so the retry path has not fired in production. A temporary probe job with the same cluster spec and retry policy confirmed that a task failing with `Network is unreachable` recovers on retry and that downstream tasks still run. The first retry fires almost immediately on a cold cluster, because the 5-minute interval counts from the start of the failed attempt. Whether a real egress outage clears within that window is still open. Details in [[ri_master_list SCD2 Reference]].
- **Classic-cluster-only caveat**: a bare serverless one-off submission of the build notebook fails reliably with `ConnectionResetError` reaching the Google Sheets API (reproduced 3/3 times) — the same known failure mode as `ri_master_list`. Ad hoc runs must use the classic cluster spec the scheduled job uses (e.g. `databricks jobs run-now 163544004016522 --json '{"only": ["ri_external_institutes_bronze"]}'`), not a plain `databricks jobs submit`. Restricting `run-now` to just `ri_external_institutes_bronze` this way leaves `standalone_silver.ri_external_institutes` stale until the next 00:23 scheduled run — the downstream `_bronze_validate`, `_silver`, and `_silver_validate` tasks don't run when `only` excludes them.
- **✅ Resolved 2026-09-03** (was: known issue as of 2026-09-02): this job's stored `notebook_task.notebook_path` for every task pointed at pre-rename paths after the 2026-09-02 notebook moves — moving/renaming a notebook in the workspace does not update a job's stored path. The 2026-09-02 15:05/14:32 runs did fail with `Unable to access the notebook` as this predicted; paths were corrected the same day and every scheduled run since has found valid paths. See [[ri_master_list SCD2 Reference]] for the parallel issue on that pipeline's tasks in the same job and its dated resolution record.

## How to update it

1. Edit the **`external_institues`** tab of the Google Sheet directly — add or change a row for an institution. Column headers must exactly match the 7-column list the notebook expects (`NEW_COLUMNS` in the build notebook).
2. Leave blank cells alone — they become `NULL` automatically.
3. Trigger a rebuild, either by waiting for the nightly job or running the `ri_external_institutes_bronze` task on demand (classic cluster — see the caveat above).
4. Downstream consumers must filter `WHERE _ROW_ACTIVE_FLAG = 'Y'` to get current state (e.g. joins against SAP customer master data on `SAP_CLIENT_NUMBER`) — there is no view doing this filtering automatically.

## Column reference

All 12 columns:

| Column | Type | Description |
|---|---|---|
| `INSTITUTION_NAME` | string | Identity column / SCD2 business key source. Unique in the source sheet. |
| `INSTITUTION_TYPE` | string | e.g. `INDUSTRY`, `UNIVERSITIES`. |
| `SAP_CLIENT_NUMBER` | string | The join key back to SAP customer master data (`lakehouse_psa_prd.sapfinance.kna1.KUNNR`). The `standalone_bronze.sap_customers` copy this note used to point at has been removed; confirmed absent from the catalog 2026-09-14. 9 nulls of 366 as of 2026-08-29 (institutions not yet matched to an SAP client). |
| `ABN` | string | Australian Business Number, formatted with spaces (e.g. `32 158 433 053`). Null for non-Australian institutions. |
| `COUNTRY` | string | |
| `STATE` | string | |
| `POSTCODE` | int | Sourced from the sheet's own `postcode` column, cast to `int`. **Was broken, fixed 2026-09-02**: from the original 2026-08-29 build through 2026-09-01, the build notebook instead overwrote this column with `col("abn").cast("integer")` — a copy-paste bug (should have read `col("postcode")`). Since `ABN` is a space-formatted string, that cast always failed silently and `POSTCODE` was `NULL` for 100% of rows the whole time. Fixed by correcting the column reference; a bronze rebuild on 2026-09-02 opened 294 new row-versions and backfilled real values for 294/366 active rows (the remaining 72 have no postcode recorded in the source sheet — genuine missing data, not the bug). |
| `_BUSINESS_KEY` | string | SCD2 identity hash. See [Change history (SCD2)](#change-history-scd2). |
| `_SURROGATE_KEY` | bigint | SCD2 per-version surrogate key. |
| `_START_TIMESTAMP` | timestamp | When this row-version became active. |
| `_EXPIRATION_TIMESTAMP` | timestamp | When this row-version stopped being active. `9999-12-31 23:59:59.999` sentinel while still active. |
| `_ROW_ACTIVE_FLAG` | string | `Y`/`N` — current version vs. historical. |

`INDEX` (a `monotonically_increasing_id()`-based row number, regenerated fresh on every run) was dropped from the pipeline entirely as part of this migration — the same fix already applied to `ri_master_list` — since it was never a stable identifier and would have caused spurious version churn in the SCD2 history.

## Change history (SCD2) mechanics

Single-column identity: **`_BUSINESS_KEY`** is a SHA-256 hash of just `INSTITUTION_NAME` — verified unique across all 366 current rows at migration time, unlike `ri_master_list`'s 8-column composite identity. A change to `INSTITUTION_NAME` is treated as a new institution (old version closes, new version opens with a fresh `_BUSINESS_KEY`), not a rename.

**How a rebuild changes history** (identical mechanism to `ri_master_list`): on each run, the notebook null-safe-compares every incoming row against every currently-active row across `_BUSINESS_KEY` + all 7 business columns. Any currently-active row with no exact match in the incoming sheet gets closed (`_ROW_ACTIVE_FLAG = 'N'`); a new row-version is inserted for every incoming row with no exact match currently active. Rows with no changes at all are left untouched — no unnecessary version churn.

**First run (bootstrap)**: since the table was a plain overwrite-only table before this migration, there was no prior history to backfill — the first run seeded every then-current sheet row as version 1, active.

## Validation notebook

`ri_external_institutes_bronze_validate` — a read-only SCD2 integrity check, independent of the build notebook, covering just this one table. It queries the table itself (no Google Sheets access), so unlike the build notebook it runs fine on serverless — no classic-cluster workaround needed for ad hoc runs.

**Naming history**: originally a single-table `validate_ri_external_institutes` notebook (2026-08-31), generalised the same day into `validate_standalone_bronze` to also cover the three `remap_*` tables (see [[Standalone Remap Tables Reference]]) once they needed the same checks. Split back apart 2026-09-02 into `ri_external_institutes_bronze_validate` (this notebook) and `remap_tables_bronze_validate` — a single combined validate notebook was judged a single point of failure, coupling two unrelated pipelines' pass/fail status together for no benefit (neither reads the other's tables).

Checks (via a `validate_table()` function, one table per notebook now): table/column existence, `_SURROGATE_KEY` uniqueness, exactly one active row-version per `_BUSINESS_KEY`, `_ROW_ACTIVE_FLAG` agrees with `_EXPIRATION_TIMESTAMP` (sentinel iff active), `_START_TIMESTAMP <= _EXPIRATION_TIMESTAMP`, no overlapping row-version windows within a business key, `_BUSINESS_KEY` recomputes correctly from the identity column(s), identity column(s) not null, active rows unique on the identity column(s), plus a non-blocking `WARN` that used to fire for the `POSTCODE`-always-null bug — silent now that the bug is fixed, but left in place in case of regression. Any `FAIL` raises. As of **2026-09-14** it is wired into alerting: the job's `email_notifications.on_failure` now names `milinda.abayawardana@monash.edu`, so a task failure here (or anywhere else in the job) sends a failure email.

**Scheduled as of 2026-09-02** (previously not scheduled) — a validation task now runs on success of the build task in job `163544004016522`. Its stored notebook path was not updated when the notebook was renamed at first, but this was **resolved 2026-09-03** (see the resolved-issue note above) — the live job's paths are correct.
